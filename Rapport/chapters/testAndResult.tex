\chapter{Testing and Results}

This chapter presents the experiments conducted to validate the correctness of our implementation, evaluate its performance on different classes of input graphs, and compare its behaviour with the original \Naut{} implementation.

The source code of our implementation is available on \href{https://github.com/roro174/nauty.git}{GitHub}.

\section{Input and output formats}

Before presenting the experimental results, we briefly describe the input and output formats supported by our implementation.

Although there is no universally accepted graph encoding for graph isomorphism algorithms, our implementation follows the convention established by \Naut{} and uses the \emph{graph6} format~\cite{mckay_graph6_formats}. This compact representation is widely used in the graph isomorphism community and provides an efficient way to store, exchange, and generate large collections of graphs while remaining fully compatible with existing tools.

The program supports five execution modes:

\begin{itemize}
    \item \textit{iso:}\label{mode:iso} compares two graphs and determines whether they are isomorphic.
    
    \item \textit{canonical:}\label{mode:canonical} computes and outputs the canonical form of the input graph in graph6 format.
    
    \item \textit{all:}\label{mode:all} computes the canonical form of the input graph and, for every leaf explored during the search, recomputes its canonical form independently to verify that all search paths produce the same canonical labelling. This mode is intended primarily for debugging and validation.
    
    \item \textit{aut:}\label{mode:aut} computes the canonical form of the input graph together with its automorphism group.
    
    \item \textit{file:}\label{mode:file} reads a collection of graphs encoded in graph6 format from a file and computes the canonical form of each graph. This mode is particularly useful for large-scale experiments and performance evaluation.
\end{itemize}

The user can also choose the node invariant used during canonical labelling. The currently available invariants are \textit{triangle}, corresponding to \hyperref[algo:invariant_triangle_by_cell]{InvariantTriangleByCell}, \textit{paths}, corresponding to \hyperref[algo:invariant_two_paths_by_cell]{InvariantTwoPathsByCell}, and \textit{triple}, corresponding to \hyperref[algo:invariant_cell_triples_by_cell]{InvariantCellTriplesByCell}.



\section{Correctness testing}

Before evaluating the performance of our implementation, we first verified its correctness through a collection of unit and integration tests covering all major components of the algorithm.

\paragraph{Unit tests.}
Each core component of the implementation was tested independently to ensure that it produced the expected output. The refinement procedure was validated on manually constructed partitions for which the refined partitions were known in advance. Likewise, the target cell selection procedure was tested on several representative partitions to verify that it consistently selected the expected target cell. Finally, each node invariant was evaluated on a variety of partitions to ensure that the computed invariant matched the expected value.

\paragraph{Canonical labelling.}
The correctness of the complete canonical labelling algorithm was verified using the \textit{all} execution mode. In addition, the \textit{file} mode was used on collections of graphs to verify that every input graph was assigned the expected canonical form. As a representative example, the graph $K_{1,3}$ was used throughout the development to validate the behaviour of the search tree and to ensure that the computed canonical labelling agreed with the expected result.

\paragraph{Pruning procedures.}
Each pruning strategy was validated independently. For pruning rule $\mathcal{P}_A$, we verified that every node whose invariant was strictly worse than the best invariant found so far was correctly discarded. For pruning rule $\mathcal{P}_B$, we verified that every node whose invariant differed from that of the current reference node was correctly pruned. Finally, pruning rule $\mathcal{P}_C$ was validated using the search tree shown in Figure~\ref{fig:nauty-tree-k13-prunned}, where every branch predicted by the theory to be removable was successfully eliminated.

\paragraph{Automorphism groups.}
The correctness of the computed automorphism groups was verified by comparing our implementation against \Naut{}. Using the \textit{file} execution mode, we computed the automorphism group of each graph in a collection of test instances and compared the results with those produced by \Naut{}. For every graph, both algorithms produced automorphism groups of identical order, providing strong evidence for the correctness of our implementation.

\section{Performance testing}
All the tests presented in the remainder of this chapter are carried out on several families of graphs: trees, sparse graphs\footnote{A graph where the number of edges is on the order of the number of vertices, placing it near the threshold for the emergence of a giant connected component.}, random graphs $G(n, 1/2)$, bipartite graphs, cycles\footnote{A graph consisting of a single cycle with at least three vertices, where each vertex is connected to exactly two other vertices.}, regular graphs\footnote{A graph where every vertex has the exact same number of neighbors.}, dense graphs\footnote{A graph where the number of edges is close to the maximum possible number of edges.}, and hypercube graphs\footnote{A graph denoted $Q_d$ whose vertices are represented by a binary strings of length $d$, with an edge between two vertices whenever they differ in exactly one bit.}. It will allowing us to observe the behavior of the invariants across a wide range of structures. For each graph family, several datasets are used, with all graphs within a given dataset sharing the same number of vertices.

The datasets were generated using \texttt{genrang}~\cite{mckay2024nug}, the random graph generation utility included with \Naut{} (version 2.9.3), using family-specific options (e.g.\texttt{-P} for edge probability, \texttt{-t} for random trees, \texttt{-r} for regular graphs (a fixed degree of 3 was used across all sizes), and \texttt{-e} for a fixed edge count). Each dataset contains 100 randomly generated graphs from the same graph class, with graph sizes ranging from 10 to 1,000 vertices. Hypercube graphs are an exception to this range: since $Q_d$ has exactly $2^d$ vertices, this family is instead tested for dimensions $d = 1$ to $10$, corresponding to graph sizes of $2, 4, 8, \ldots, 1024$ vertices. As $Q_d$ is unique up to isomorphism for a given dimension, it was instead generated once using \texttt{genspecialg} (option \texttt{-Q})~\cite{mckay2024nug} and then relabeled 1,000 times using \texttt{ranlabg}~\cite{mckay2024nug} to obtain 1,000 distinct labelled instances per dimension. To ensure that all experiments are reproducible and performed on exactly the same inputs, the datasets were generated only once prior to the experiments and stored as graph6 files. Consequently, every benchmark reported in this chapter is performed on the same collection of graphs.

Several experiments are then performed on these datasets. First, we measure and compare the running time of all our invariants across the different datasets, and against the default version of \Naut{}. A Wilcoxon test is used to statistically compare the invariants against one another. We also measure the pruning ratio achieved by each invariant on each graph family. Finally, we evaluate our version of \Naut{} on the same graphs with pruning disabled, in order to isolate the effect of the pruning rules themselves.

All running times are measured in wall-clock (real) time. Experiments were conducted on a Lenovo IdeaPad 3 15ITL6 laptop equipped with an 11th generation Intel Core i3--1115G4 processor (x86\_64 architecture) running at 3.00\,GHz, 7.6\,GiB of RAM, and Ubuntu 24.04.1 LTS (kernel version 6.8.0--51-generic). This machine was dedicated exclusively to the experiments, with no other process running concurrently, and no time limit was imposed on the executions.

\subsubsection{Discussion of the results}

La première chose ici que nous pouvons observer c'est qu'il est très très compliqué de battre l'implémentation originale de \Naut{} sur tous les classes de graphes. Comme énoncé, l'implémentation originale de \Naut{} est extrêmement optimisée et a été développée et testée pendant de nombreuses années. Il est donc naturel que notre implémentation, bien que correcte et fonctionnelle, ne parvienne pas à surpasser \Naut{} en termes de performance sur toutes les classes de graphes. Ça reste tout de même intéressant de voir la différence entre nos 2 implémentations. On remarque surtout que l'implémentation originale de \Naut{} reste beaucoup plus performante sur les graphes sparse, trees et les graphes réguliers car on remarque vraiment une énorme différence dans les temps moyens d'éxecutions.  

Ensuite, si on se concentre sur notre implémentation et qu'on compare les 3 invariants, nous pouvons voir que pour une première partie de classe de graphes, les invariants reste assez proche les uns des autres, mais pour les trees, les graphes sparse et les graphes réguliers, on remarque que l'invariant \textit{triple} est beaucoup plus coutant que les 2 autres. Il y a une vraie différence dans leur temps d'execution. Ce qui montre que les 2 autres invariants restent mieux ``par défaut'' pour ces classes de graphes.

Le Wilcoxon test ne fais que confirmer ces propos.

\FloatBarrier\subsubsection{Discussion of the results}

Avec ces différentes classes de graphes, beaucoup de caractéristiques sautent aux yeux. Tout d'abord, on peut remarquer que les graphes aléatoires $G(n, 1/2)$, les graphes bipartites, les hypercube et les graphes denses ont un nombre de noeuds et de feuilles visités relativement faible. La plupart des graphes ont un nombre de noeuds et de feuilles visités égal à 1, ce qui signifie que l'algorithme a trouvé la solution optimale dès la fonction de refinement initial. Ce qui n'est pas le meilleur moyen de tester nos prunning mais démontre bien pour les graphes aléatoires $G(n, 1/2)$, almost all graphs can be canonically labelled in linear time by a simple refinement procedure as cited in the state of the art~\cite{babai1980random}. Pour les autres graphes, cela vient du fait qu'ils sont très structurés et que la fonction de refinement est très efficace pour trouver la solution optimale. 

Cependant, là où on peut vraiment voir l'efficacité du prunning se trouve dans les autres catégories de graphes. Tout d'abord, le point le plus crucial que nous pouvons observer est que le prunning $\mathcal{P}_C$ est le plus efficace pour tous les graphes. Il est quasi à 100 pourcent pour tous les graphes qui ont subi du prunning. Ça peut s'expliquer par plusieurs raisons. La première est que nos méthodes invariants ne sont peut-être pas très bien adaptées pour les graphes que nous avons testés. En effet, les invariants que nous avons choisis sont très simples et ne sont pas très discriminants. Donc lors des comparaisons d'invariants par node, on arrive à trouver des noeuds qui ont le même invariant et donc on ne peut pas pruner. La deuxième raison est le groupe d'automorphisme est énorme, ce qui permet de faire une énorme quantité de prunning par automorphism. et comme notre prunning par automorphisme se passe avant le prunning par invariants, cela fait que le prunning par invariants est très peu efficace comparé au prunning par automorphisme.
